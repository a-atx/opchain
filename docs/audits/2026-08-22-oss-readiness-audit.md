## Lens: arch-boundary

Dependency map of opchain's site/worker/build tooling vs. the product (skills/, plugins/, mcp/, .claude-plugin/). Of the 13 scripts + 10 tests + content.config.ts in scope, 9 scripts and 6 tests actually read skills/ (the rest are HTTP-, site-, or .checkpoints-only). The coupling is bidirectional and concentrated in five seams: (1) scripts/gen-skills-catalog.mjs validates SKILL.md frontmatter against the SITE's feature-flag registry (src/lib/flags/registry.js, which hardcodes every skill id and command verb); (2) the hosted MCP + /skills.json + /llms.txt + zips all derive from a skills tree at build time (gen-mcp-catalog → src/generated/mcp-catalog.json; sync-docs → public/docs; make-skills-zip → public/*.zip); (3) mcp/local-server.mjs imports ../scripts/gen-mcp-catalog.mjs and ../src/lib/mcp/server.js, so the MCP core and routing table are product code living under src/lib; (4) the skills themselves instruct users to run monorepo-only tooling (scripts/checkpoint.mjs, npm run checkpoint:*, src/generated/api-dev-adapters.json) that no distribution channel ships — confirmed by docs/audits/2026-07-04-portability-audit.md; (5) oc-stack-forge packs feed both product runtime (pack-dispatch.js, api-dev adapters) and site pages/flags (coverage-flags.json, packs-catalog.json). Plus the Astro content collection globs ../skills and shells `git log -- skills/<id>`, and two symlink farms (plugins/opchain/skills → ../../skills; .claude/skills/* → ../../skills/<name>, CI-enforced) assume skills/ sits at the repo root. Release versioning is lockstep across both halves (skills/*/SKILL.md version ↔ four site files ↔ /skills.json catalogVersion). Current state: everything is green (validators pass; 188 tests in the 10 listed suites pass), the monorepo is already public with 0 forks, and the "private upstream" mirror model is both inaccurate and hostile to contributors. Three boundary options are compared below; recommended path is B immediately (make the already-public monorepo the honest contribution target, retire the force-push mirror) followed by A (invert the mirror, product repo = source of truth consumed by the site as an npm package + git tag) executed as seam-cutting PRs inside the monorepo first, keeping `skills/` path-stable so the plugin symlink and marketplace command keep working. ## Lens: license-research

Research lens: open-source licensing for NVIDIA-class enterprise adoption of the opchain skills/plugin/MCP code. Repo state today: a single root MIT LICENSE ("Copyright (c) 2026 asfbay-bit" — a GitHub handle), zero SPDX headers, no NOTICE/SECURITY/CODE_OF_CONDUCT/CODEOWNERS, no `license` field in either package.json, no DCO/CLA or contribution-license language in mirror/CONTRIBUTING.md, and the product's own download channel (opchain-skills.zip + per-skill zips from scripts/make-skills-zip.sh) ships NO license text at all — a literal breach of MIT's own notice condition and the first thing an OSPO scanner flags. Research findings: (a) MIT and Apache-2.0 are both OSI-approved "notice"-class licenses that land on every permissive allowlist (Google's third-party policy, Blue Oak Silver, NVIDIA's own SDK EULA defines OSS as OSI-approved), but Apache-2.0 adds the express patent grant (§3), the inbound=outbound contribution clause (§5), the trademark carve-out (§6) and the NOTICE mechanism — and it is what NVIDIA ships outbound on every checked repo (NeMo, TensorRT-LLM, cuda-python, nvidia-container-toolkit, NeMo Agent Toolkit: all Apache-2.0 with `SPDX-FileCopyrightText`/`SPDX-License-Identifier` headers). (b) Every checked NVIDIA repo requires DCO `Signed-off-by` (git commit -s), as do CNCF/LF; Google and ASF use CLAs, which LF and practitioners describe as adding friction and corporate legal/HR review; GitHub ToS §D.6 already makes inbound=outbound the default. (c) SPDX short IDs + REUSE 3.3 (LICENSES/ dir, per-file tags or REUSE.toml, `reuse lint`) is the lint-able standard; npm's `license` field expects an SPDX expression. (d) Anthropic licenses its open skills Apache-2.0 per-skill (docx/pdf/pptx/xlsx are source-available) and its claude-code repo is "All rights reserved / Commercial Terms"; prompt repos are MIT (fabric), CC0 (awesome-cursorrules) or split (awesome-chatgpt-prompts); docs sites use CC-BY-4.0, which CC itself says not to apply to software. (e) Neither license grants trademark rights; "opchain" has no exact USPTO hit surfaced, but Linux Foundation owns a LIVE registration for OPENCHAIN (Reg. 5242152, classes 9/42, "software license compliance") — an adjacent-field near-collision worth a formal clearance; opchain.com is parked for sale, npm/PyPI names are free. (f) ~38% of commits are Claude co-authored; Anthropic's consumer and commercial terms assign output rights "if any"; the USCO Part-2 report (Jan 2025) and Thaler v. Perlmutter (D.C. Cir. 2025, cert denied 2026-03-02) mean purely prompt-generated text may be unprotectable, which does not block licensing (you can only grant what you own; the grant is harmless over public-domain material) but does mean the defensible asset is the human-curated compilation — mitigate with provenance trailers, an ASF-style AI-contribution policy, and DCO. Recommended package: relicense the product repo to Apache-2.0 (clean — no external human copyright holders in git history), copyright line in a legal name/entity not a handle, NOTICE + TRADEMARKS.md, REUSE-compliant SPDX tags, DCO (no CLA), Apache-2.0 for SKILL.md too (CC-BY-4.0 only for site prose if desired), and community health files.
